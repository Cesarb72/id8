## **What This Project Is**

Arc is a modular coordination engine designed to operate at the intersection of real-world complexity and human intent. It is deterministic, auditable, and domain-agnostic. ID.8 is Arc’s first vertical product — a consumer nightlife concierge for San Jose that proves the engine works under real-world chaos. ID.8 is Arc’s proof of concept and a product in its own right simultaneously. The PDD you are reading is the single source of truth for ID.8 product decisions. The Arc System Living Doc is the source of truth for engine architecture. They cover different scopes and neither overrides the other.

## **The Three-Layer Work Structure**

**Layer 1 — Claude (this chat)**

Strategy, documentation, architectural decisions, and the living document layer. This is the “what and why” layer. Decisions get made here, locked into the PDD, and then handed to the build layer. Claude reads all project docs at the start of each session, integrates updates into the PDD and affected living docs, and then moves into strategic or architectural conversation. The PDD decision log gets a new entry every time something material changes.

**Layer 2 — ChatGPT + Codex (current build environment)**

Implementation. The “how and build” layer. This is where specs and architectural decisions from Claude become actual code. Codex operates on the ID.8 codebase directly. The operating rules that govern Codex work — the full-seam sweep protocol, the patch diagnostic, the hardening queue sequence — are defined in this PDD and in the Arc Production Contract. When something is built or fixed in Codex, the outcome gets reported back to Claude and logged in the PDD decision log. Codex does not define architecture — it executes it. This arrangement is temporary: once the current ID.8 build is complete, all development moves to Claude.

**Layer 3 — Full Claude (after this project)**

After ID.8 is complete, all Arc System development moves to Claude — strategy and build unified in one environment. The planned approach uses Claude’s agentic capabilities to build out the broader Arc engine stack. This is architecturally natural: Arc’s engine stack (Field, Interpretation, Bearings, Waypoint, LCE) maps directly to an agent-node architecture. Each engine becomes a real agent with memory, tool use, and defined handoff contracts. This is the next phase pivot — not current scope, but being scoped now.

# **4. New Operational Rule — Full-Seam Sweep Before Patching**

For any non-trivial engine behavior issue with multiple plausible seams, run a full-seam read-only sweep before touching code. This rule was learned during the Surprise debugging sequence and is now permanent operating protocol.

**For non-trivial engine issues: run a full-seam read-only sweep across all plausible causes before any patching. The choke point may be downstream of the first visible seam. Patching the wrong seam wastes time and may mask the real cause.**

Exceptions to this rule — sweep can be skipped when the issue is obviously: a direct regression from the last patch, a syntax or runtime error, a clear one-file wiring break, or a trivial UI bug with no engine ambiguity.

| **STEP** | **ACTION** |
| --- | --- |
| **1 — Observe** | Document the behavior fully. What is the symptom? What surface? What flow? When does it appear? |
| **2 — Full-seam read-only sweep** | Identify all plausible seams that could cause this behavior. Read-only audit across all of them. Do not touch code yet. |
| **3 — Rank likely seams** | Based on the sweep, rank causes by likelihood and proximity to the actual symptom. |
| **4 — Patch top seam only** | Make one targeted change. The smallest change that addresses the top-ranked seam. |
| **5 — Re-test once** | Run the test. Did it fix the behavior? |
| **6 — If still unresolved: re-sweep** | Do not blindly patch again. Run another full-seam sweep from the new state. The choke point may be downstream of where you patched. |

# **7. Canonical User Flow**

*The three modes are not three different products. They are three different entry strategies into one shared Plan Build pipeline. Modes seed and constrain the pipeline — they do not own separate build systems. Mode differences end at contract entry. Artifact lineage is shared from preview onward.*

**Structural Rule**

ID.8 uses one shared Plan Build pipeline. Modes do not build plans separately — they seed and constrain a shared pipeline that owns live/API ingress, runs the engines, and produces candidate plan artifacts that are then expressed differently per mode. Mode differences end at contract entry. Artifact lineage is shared from preview onward. All three modes must produce a SelectedRouteArtifact by the end of Step 2. Step 3 — Shared Plan Preview — and all downstream review surfaces must render from that same artifact lineage until commit produces the RuntimeRouteArtifact.

*One-line canonical rule: Modes differ in how candidates are produced and chosen; they converge on the same Step 3 — Shared Plan Preview once a candidate is selected.*

**Artifact Ladder**

**ContractEntryArtifact** — Interpretation-owned candidate route truth. Promoted from the existing CanonicalCandidateRouteArtifact / Step 2 candidate artifact pattern. Carries artifact id, direction identity, route identity, story spine, proof/rationale, anchor/highlight identity, and provenance lineage. This is the only artifact that differs by mode. Surprise: system-seeded Plan Build request. Curate: guided candidate comparison from the shared pipeline. Build: explicit user-authored Plan Build request.

**SelectedRouteArtifact** — Application-projected active selected truth. Already exists in partial form. Should become a shared projection contract, not page-local logic. Drives Step 3 — Shared Plan Preview: route identity, why-this-route rationale, stop sequence, and pre-commit adjustments. All three modes must converge into this artifact before Step 3 — Shared Plan Preview renders.

**RuntimeRouteArtifact** — Waypoint/planning-owned committed/generated route truth. Unify the current fragmented responsibilities spread across CanonicalRouteArtifact, FinalRoute, and live/session payloads. Drives the live journey, LCE co-pilot, swap suggestions, timing updates, and Plans Hub save. Owned by LCE from this point forward.

**Mode Entry Flows — Entry Strategies, Not Separate Build Systems**

**Surprise Me** — System auto-generates a plan preview (ContractEntryArtifact). User can regenerate or continue. Continues to Journey Map / Story Spine for review and edit before commit. Live journey artifact produced and saved to Plans Hub.

**Curate Experience** — Curate is the comparison and discovery phase that leads into Step 3 — Shared Plan Preview. ContractEntryArtifact (the user-facing “plan contract”) is the canonical term for all mode-specific candidate artifacts — this alias is defined once here. User compares and chooses from deterministically built ContractEntryArtifacts derived from the selected starter signal. These are not pre-authored static plans — they are scenario-built route options produced by the pipeline from the starter signal. The “Explore what’s possible” experience belongs here, at the decision point, not inside the preview contract. Curate = choose ContractEntryArtifact → preview → refine route → commit live plan. Once a ContractEntryArtifact is chosen, Curate routes into the shared Step 3 — Shared Plan Preview, not a separate mode-specific preview shell. Live journey artifact produced and saved to Plans Hub.

**Build My Plan** — User provides location, anchor query, and persona. Find Anchors surfaces candidates. User selects an anchor, which produces a custom plan card (ContractEntryArtifact). User can restart or continue to Journey Map / Story Spine. Live journey artifact produced and saved to Plans Hub. Note: anchor selection UX needs a dedicated pass — functionally valid, not product-clean yet. Tracked in Open Questions.

**8. Hard Rules — Non-Negotiable**

**Canonical Ownership Gate (added Block 7 / Savepoint 6)**

*Before introducing any new type, contract, artifact, helper, adapter, or source-of-truth object, stop and ask: (1) Does an existing canonical artifact already serve this job?
